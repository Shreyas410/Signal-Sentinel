Signal Sentinel Open the analyst console

Signal Sentinel turns public threat feeds into detection rules, and enforces a rule only after a security analyst approves it.

Each approved rule is enforced in one of two places: the CI pipeline that checks code before it ships, or the app your customers use to read their messages.

How a rule gets enforced

  1. Public threat feeds

    The CISA Known Exploited Vulnerabilities catalog and the OpenPhish community feed, fetched on demand. If the network is down, the last local copy is used and the console says so.

  2. Rule drafted

    A newly exploited CVE in a weakness class the scanner can express as a pattern becomes a draft code rule. A newly reported phishing URL becomes a draft domain block.

  3. Analyst approves

    Nothing is enforced until a person reads the rule, the feed entry behind it and what it would match, then clicks Approve and Confirm.

  4. Enforced

    Code rules go to the Dev/CI scanner. Domain rules go to the Customer Shield link firewall.

The two enforcement layers

Layer 1 · Dev/CI pipeline

Before code ships

Scans every .py, .js and .ts file in a repository against the enforced code rules, and checks requirements.txt pins against known-vulnerable versions.

  • Each finding shows its severity, file, line and the code that matched.
  • Verified one-click fixes rewrite the line only if the file still matches what was scanned.
  • The demo runs against two intentionally vulnerable repositories: core-customer-api and payments-service.
Layer 2 · Customer-facing app

When a message arrives

Scores the wording of an incoming message and every link inside it. Links are checked against the enforced domain blocklist, lookalike brand names and high-risk domain endings.

  • The link check reads the destination domain only, never the message content, so it works the same for SMS, email or encrypted chat.
  • Every link gets a plain verdict: BLOCKED, SUSPICIOUS or ALLOWED, with the reason.
  • Customers who already clicked get a recovery checklist.
